# Releases

The owner approves a public release by pushing `v<server version>`. For example,
server version `0.1.2` requires tag `v0.1.2`. The app version must match the
server version. The workflow rejects mismatched tags. Do not create the first
tag before owner approval.

The `release` workflow builds natively on Ubuntu 22.04 x86_64 and arm64
(glibc 2.35), and macOS 15 Apple Silicon. Manual dispatch and pull requests
that change `.github/workflows/release.yml` produce workflow artifacts only.
The PR trigger lets the workflow be verified before it exists on main.
Only a tag push can reach the job with permission to create a GitHub Release.

The combined `hyperthymesia-release` artifact contains:

- `hx-server-<version>-linux-x86_64.tar.gz`
- `hx-server-<version>-linux-aarch64.tar.gz`
- `hx-server-<version>-macos-aarch64.tar.gz`
- `Hyperthymesia-<version>-macos-aarch64.zip`
- `install.sh`
- `SHA256SUMS`

Asset versions use the Cargo version without the tag's leading `v`. Server
archives contain root-level regular files: `hx-server`, `LICENSE`, `SOURCE`
(public repository URL and commit), and `THIRD-PARTY.txt` generated by
`cargo-about`. The macOS archive also includes `hx-vision-ocr`. The app zip
contains only `Hyperthymesia.app/` members, with no symlinks. Its Resources
directory includes the same license and source notices. fx is never bundled;
the real installer downloads it separately and checks its pinned hash.

Each build runs the shipped installer with `--dry-run`, a scratch HOME, and
`HX_RELEASE_BASE=file://<asset-directory>`. This requires access to the pinned
fx release; download failures fail CI with diagnostics. Two fresh Linux jobs
in pristine `ubuntu:22.04` containers, with no added packages, Rust, database
or fx, extract the server and assert
its `--version` output with an empty environment. The combined artifact is
assembled only after those checks pass. Its checksums use bare filenames and
exactly two spaces between hash and filename.

## Apple signing

Without Apple secrets, releases use ad-hoc signatures. Signed releases require
all of these repository Actions secrets:

- `APPLE_CERTIFICATE_P12_BASE64`: base64-encoded Developer ID Application p12
- `APPLE_CERTIFICATE_PASSWORD`: p12 import password
- `APPLE_SIGN_IDENTITY`: full `Developer ID Application: ...` identity
- `APPLE_ID`: notarization account
- `APPLE_TEAM_ID`: developer team
- `APPLE_APP_PASSWORD`: app-specific notarization password

A partially configured set fails visibly. On dispatch and tag runs only,
the macOS runner imports the certificate into a temporary keychain, signs
with hardened runtime and timestamps, submits the app and standalone server
executables for notarization, and staples the app ticket before packaging.
The final app zip is extracted again to verify its signature and stapled ticket.
The temporary keychain and p12 are removed even if the build fails. PR runs
use ad-hoc signing. Keychain writes belong exclusively to the hosted runner.
The standalone tar cannot carry a stapled ticket; Gatekeeper retrieves its
notarization ticket online.

For an isolated local build, install `cargo-about` 0.9.3 and run:

```sh
CARGO_TARGET_DIR="$(mktemp -d)/target" \
HX_RELEASE_DIR="$(mktemp -d)/assets" scripts/build-release.sh
```

The release script builds the app in its scratch directory and explicitly
selects ad-hoc signing by default. It does not start services or read user
state. `scripts/build-app.sh` also supports `HX_APP_OUTPUT` for an isolated
app destination. Release output directories must be empty to prevent stale
assets from entering a release.
